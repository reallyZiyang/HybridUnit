# UniKit UI Prefab Builder

## First Pass

Before editing, inspect the current project state instead of relying on memory:

- `Assets/Res/UI`
- `Assets/AssetBundleCollectorSetting.asset`
- `Packages/UniKit-UI/Runtime/Core`
- `Assets/Scripts/Game/Play/Runtime/UI`
- the provided mockup/effect image

Run `scripts/audit_unikit_ui_resources.py <project-root>` when path or collector rules matter. The script is read-only.

## Workflow

1. Copy `templates/ui-screen-spec.yaml` to a task-local spec file and fill it from the mockup before creating assets.
2. Validate the spec with `scripts/validate_ui_spec.py <project-root> <spec>`.
3. Decompose the mockup into Unity UI objects: View, Panel, Item, background, buttons, text, icons, lists, effects, masks, tips, and dynamic data areas.
4. Decide the UI type:
   - Full screen or independently opened page: `UIView`
   - Reusable section inside a page: `UIPanel`
   - Ordinary component, list item, or lightweight reusable block: `UINode`
5. Place assets using the project paths in `references/project-paths.md`.
6. Build the final prefab with uGUI components and UniKit conventions. Do not modify framework code.
7. Add `UIDataBinding` to prefab roots, set its `type`, and bind only nodes that runtime code needs.
8. Whenever a prefab's runtime binding references change, run the UniKit Scanning flow (`UIDataBindingUtilities.FindAllBindItems(binding)` or the inspector `Scanning` button), review the resulting `bindItems`, then generate UI code through `UIDataBindingUtilities.Generate(binding)`.
9. By default, stop after producing the prefab and UniKit-generated UI class plus `*.Bindings.cs`. Only add behavior code when the user explicitly asks for interaction, navigation, data rendering, or business integration.
10. Validate prefab references, YooAsset keys, atlas usage, and visual fidelity against the mockup.
11. Render or screenshot the completed prefab and compare it against the reference mockup. If major structural elements such as title, banner, panels, stat backgrounds, buttons, or progress bars are visibly off, regenerate the responsible asset or adjust layout before accepting the result.

## Hard Rules

- Name View prefabs with the `UI_` prefix, e.g. `UI_MainMenuView.prefab`; runtime opens `MainMenuView` through `UIManager.Open<MainMenuView>()`.
- Keep runtime asset keys extensionless file names. The project uses YooAsset `AddressByFileName` and `SupportExtensionless`.
- Put UI sprites in atlas-backed sprite folders, not in arbitrary resource folders.
- Use explicit atlas loading for UI images, e.g. `SetAtlasSprite(UIAtlas.k_Menu, spriteName)` or `SetAtlasSprite("SA_UI_Icon", spriteName)`.
- Use `SetIcon(name)` or `SetSprite(name)` only after confirming their inferred atlas names exist.
- Use bind prefixes consistently: `Btn`, `Txt`, `Img`, `Tog`, `Sld`, `Input`, `Ddl`, `List`, `Scroll`.
- Keep generated files separate from hand-written files. Put custom behavior in the main partial class generated by UniKit only when behavior is explicitly in scope.
- Default UI work must not add button handlers, navigation calls, render methods, `[UIDataReceiver]`, fake data, logging placeholders, or business integration.
- If a bound node is added, removed, renamed, or changes target component type, regenerate through `UIDataBindingUtilities.Generate(binding)` after Scanning and bind-item review. Never patch generated fields by hand.
- Do not hand-write `*.Bindings.cs` files, generated binding fields such as `m_BtnStart`, or `OnInitBindings()`.
- Do not generate `MainMenuView.cs`, `BattleView.cs`, or any UI class by writing C# text from a custom builder script. The main UI class must be created by UniKit `UIDataBindingUtilities.GenerateUIClass` through `UIDataBindingUtilities.Generate(binding)`.
- A custom builder must not contain methods like `PatchMainMenuBehavior()` that write UI class files. After UniKit creates the class, only patch or edit the behavior body that belongs to the task, and never replace the generated class wholesale.
- Do not use `scripts/render_runtime_class.py` as the default project code-generation path. It is only an offline drafting aid; real UI class and binding files must come from `UIDataBindingUtilities.Generate`.
- Do not deliver a build script, menu command, generator, or "run this in Unity" instruction as the result. The default deliverable is the final prefab, sprites/materials, and generated DataBinding code; include hand-written behavior code only when the user explicitly asks for logic.
- Temporary editor automation is allowed only as an implementation detail. If an editor helper is created to build a prefab, run it, verify the final assets, then remove the helper before finishing unless the user explicitly asks to keep it.
- If Unity is already open and batchmode is blocked, use the open Unity instance or another available automation path to produce the final prefab. Do not stop with a build script as a substitute for the prefab.
- Do not run destructive git or filesystem cleanup while creating UI.
- For every Image, decide whether it is fixed-size art or stretchable UI. Stretchable surfaces such as panels, buttons, stat tiles, and bar slots must use a sprite prepared with the project `UISpriteSlice.SetBorder3` logic and Image `Type = Sliced`; icons, avatars, confetti, ribbons, and other decorative art should remain Simple unless intentionally stretched.
- `UISpriteSlice.SetBorder3` means the UniKit editor tool at `Packages/UniKit-UI/Editor/Tools/UISpriteSlice.cs`: set `TextureImporter.isReadable = true`, set `spriteBorder = (texture.width / 3, texture.height / 3, texture.width / 3, texture.height / 3)`, then reimport with `ImportAssetOptions.ForceUpdate`.
- If UI-building automation cannot use Unity Selection/MenuItem safely, add a small project Editor-only static helper that applies the same SetBorder3 algorithm to explicit texture asset paths. Do not hand-pick arbitrary border numbers in prefab or `.meta` generation.

## TMP Text Style Rules

- Ordinary UI text must be rendered by TMP. Do not bake button labels, panel copy, stats, numbers, or localized text into PNG sprites.
- Create a dedicated TMP material variant for each visually distinct mockup text style, such as white button text with dark brown outline, small title text with thick shadow, or dark stat text with light outline.
- Store shared TMP material variants under `Assets/Res/UI/Common/Material/` and name them by role and appearance, for example `TMP_Button_WhiteBrownOutline.mat`.
- Use TMP material properties for face color, outline, glow, and underlay shadow. Do not duplicate the same label into multiple TMP/Text objects to fake outline, shadow, or stroke thickness.
- If a mockup text effect cannot be matched with one TMP material variant, keep the closest material-only version and report the mismatch in the final summary instead of adding extra text controls.
- A TMP node may use the base font material only for plain text with no outline, no glow, and no shadow.

## Prefab Text Encoding Rules

- Prefer setting TMP text through Unity Editor APIs and letting Unity serialize the prefab.
- If prefab YAML must be generated or patched directly, write non-ASCII `m_text` values as Unity-compatible `\uXXXX` escapes, for example `m_text: "\u5F00\u59CB\u6218\u6597"`.
- Do not write Chinese prefab text through PowerShell here-strings, default console encodings, or temporary scripts without explicit UTF-8 handling.
- Python or other scripts that read/write prefab YAML must use explicit UTF-8 and must escape non-ASCII text before writing `m_text`.
- After generating or modifying any prefab containing localized TMP text, scan for accidental replacement text with `rg 'm_text: "\?\?+' Assets/Res/UI`. Treat matches as failures unless the design intentionally contains question marks.

## Runtime Patterns

- Register button callbacks in `OnInit()` with `SetOnClick`.
- Only register callbacks after the `UIDataBinding` generated fields exist.
- Refresh data through a clear `Render`, `Refresh`, or `[UIDataReceiver]` method.
- Use `ListView`, `ScrollView`, or `InfiniteScrollView` for repeated UI; name the template child `Template`.
- Use `BindItems<TData,TItem>()` for simple list data binding.
- Use `UIContextNode` when a non-controller UI node needs `GameContext`.
- Use `UIEffect` for UI particles, `UIPointerEventPass` for click-through masks, and `UIUtilities.PlaceTips` for bounded tooltip placement.

These runtime patterns apply only when behavior is in scope. If the user only asks to make a UI screen or prefab, generate the empty UniKit view class and bindings, then leave behavior methods empty.

## Templates and Scripts

- `templates/ui-screen-spec.yaml`: canonical structured input for one UI screen.
- `templates/UIView.cs.tmpl`, `templates/UIPanel.cs.tmpl`, `templates/UINode.cs.tmpl`, `templates/ListItem.cs.tmpl`: offline drafting templates only, not the default generation path.
- `scripts/validate_ui_spec.py`: checks the screen spec and prints prefab, asset, binding, and runtime plans.
- `scripts/render_runtime_class.py`: offline drafting aid only; do not use it as the default project generation path.
- `scripts/audit_unikit_ui_resources.py`: checks project resource placement, YooAsset collector rules, duplicate short keys, atlas coverage, and UISettings output mapping.

## Validation Checklist

- The filled screen spec passes `validate_ui_spec.py`.
- `Assets/Res/UI` contents match the collector rules.
- New prefabs are under a collected prefab path.
- New sprites are under a sprite folder packed by an `SA_UI_*` atlas.
- New runtime code is under `Assets/Scripts/Game/Play/Runtime/UI/View`.
- `UIDataBindingUtilities.Generate(binding)` succeeds and creates/updates the UI class and `*.Bindings.cs`.
- The main UI class file was created by UniKit generation, not emitted by a task-specific script.
- Generated fields match intended nodes, and no generated binding file was hand-edited.
- No task-specific editor build script remains as the primary deliverable.
- Unity reports no missing script, sprite, material, font, or atlas references.
- If behavior is in scope, the page can open via `UIManager.Open<T>()`, close cleanly, and handle empty/long/dynamic data. If behavior is not in scope, do not add logic just to satisfy this check.
- Screenshot comparison against the mockup checks layout, hierarchy, text fit, button hit areas, list extremes, masks, and disabled states.
- Screenshot comparison is blocking for visual UI work: if key shapes or proportions differ clearly from the mockup, do not accept the prefab until the asset or layout is regenerated/adjusted.
